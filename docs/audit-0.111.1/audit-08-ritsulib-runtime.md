# RitsuLib 运行时 审计（0.111.1）

All patches applied` 与 `Shared framework initialization complete.` 是否出现；③ 把诊断改挂 `ModelRegistryInitializedEvent` 或 `RunStartedEvent`（见改进机会），不依赖 NGame 生命周期。

## 潜在 Bug / 行为差异（mod 逻辑 vs 0.111.1 语义）

1. **Entry.Init 的调用顺序隐患**（`Scripts/Entry.cs:19-39`）：`harmony.PatchAll(assembly)`（:28）与 `MinionLayoutManager.Register(...)`（:35）排在 `ModTypeDiscoveryHub.RegisterModAssembly`（:32）和 `RegisterMerchantDiag`（:38）之前。若 `PatchAll` 或 `MinionLayoutManager.Register` 抛异常，`RegisterModAssembly`/`RegisterMerchantDiag` 不会执行。此时内容仍可能被注册——RitsuLib 的 `ModTypeDiscoveryHub.RunOnce` 的扫描来源同时包含 `ModManager` 已加载模组的程序集（RL:Interop/ModTypeDiscoveryHub.cs:280-302，`Sts2ModManagerCompat.BuildLoadedModAssemblyListsByManifestId`），即"Init 抛异常但卡照常注册、诊断却永远静默"的组合是真实可能的；且 Jaina 的 manifest（`jaina.json`）依赖 `STS2-RitsuLib>=0.5.4` 与 `MinionLib>=0.6.2`，依赖先加载（0.111.1:Core/Modding/ModManager.cs:718-785 要求依赖 `state==Loaded`），RitsuLib 的 `Initialize()` 一定先于 Jaina 的 `Init()`。
2. **`GameReadyEvent` 的触发时机早于 `ModelDb.Init` 的可能性**：`NGame._Ready`（0.111.1:NGame.cs:182）由 Godot 场景树驱动，而 `GameStartup` 是 `_EnterTree` 里 `TaskHelper.RunSafely(GameStartupWrapper())`（NGame.cs:174）异步推进，`OneTimeInitialization.ExecuteEssential`（含 `ModelDb.Init`，0.111.1:OneTimeInitialization.cs:68-86）在其中 `await ExecuteVeryEarly`（Steam/云存档等）之后才执行。若 `_Ready` 早于 `ExecuteEssential` 完成，诊断回调里 `ModelDb.CardPool<JainaCardPool>()` 会抛 KeyNotFoundException——已被 try/catch 覆盖成 `[JainaDiag] ERROR` 行，但说明该事件不适合做"内容就绪"信号。
3. **关键词悬停双路径**：Jaina 的 `AdditionalHoverTips`（`JainaSpellCardTemplate.cs:23-32`、`JainaMinionCardTemplate.cs:71-80`）对每个 `CanonicalKeywords` 调 `HoverTipFactory.FromKeyword`；而 0.111.1 的 `CardModel.HoverTips`（0.111.1:CardModel.cs:953-988）本身也会遍历 `Keywords` 调同一工厂。两份提示靠 `list.Distinct()` 去重——0.111.1 中 `HoverTip` 是 **`record struct`**（0.111.1:Core/HoverTips/HoverTip.cs:8），值相等去重生效；RitsuLib 路径下两次 `CreateHoverTip`（RL:Keywords/ModKeywordRegistry.cs:518-529）产出的 `Id/Title/Description/Icon` 相同，等值成立。行为 OK，但属于隐性依赖：若未来 `HoverTip` 改回引用类型，会出现重复词条。
4. **动态关键词未注册前的显示回退**：0.111.1 的 `CardKeywordExtensions.GetTitle/GetDescription`（0.111.1:CardKeywordExtensions.cs:10-28）对未知枚举值走 `Slugify(ToString())` 生成数字本地化键，不抛异常但显示缺失文本。RitsuLib 的 `HoverTipFactoryFromKeywordPatch`（RL:Keywords/Patches/HoverTipFactoryFromKeywordPatch.cs:40-47）只对 `ModKeywordRegistry.TryGetByCardKeyword` 命中（即 `[RegisterOwnedKeyword]` 已注册）的值短路；若 Jaina 某卡在注册冻结前（`ModelDb.Init` 时冻结，RL:ModKeywordRegistry.cs:99-116）就读取关键词，会退化为数字键文本。当前 Jaina 的关键词都在 `LocManager.Initialize` 的自动注册阶段完成、`ModelDb.Init` 之后才被卡读取，无实际触发路径。
5. **`Frostbolt` 商店候选——代码层面排除的假设**（详见下节 H3/H4）：0.111.1 商店管线（`MerchantInventory.cs:98-112` → `MerchantCardEntry.cs:69-94` → `CardFactory.cs:40-60/263-281`）确认：Shop 稀有度掷骰含 Common（`CardRarityOdds.cs:39-41`：ShopCommonOdds=0.54/0.585），`GetNextAllowedRarity` 对"只有 Common+Uncommon 攻击"的池在掷到 Rare 时会回绕到 Common（`CardRarityExtensions.cs:14-31`：Rare→Common），`Frostbolt(Common,Attack)` 与 `ApexisBlast(Common,Attack)` 同为候选；`FilterForPlayerCount`（`CardFactory.cs:25-32`）对默认 `MultiplayerConstraint=None`（`CardModel.cs:296`）的卡不拦截；`MerchantCardEntry.Populate` 的 `_cardPool.Except(second)`（`MerchantCardEntry.cs:71-74`）只排除已上架卡，不排除 Frostbolt。若按源码推演，Frostbolt 应在约半数商店出现——实际观察不到，必是运行时状态问题（见下节 H1/H2/H5）。

## 商店候选之谜（Frostbolt 缺失）——可验证假设

0.111.1 候选生成链路（已逐行核对）：`MerchantInventory.PopulateCharacterCardEntries`（MerchantInventory.cs:98-112，5 个槽：Attack×2/Skill×2/Power×1，`:15-22`）→ `MerchantCardEntry.Populate`（MerchantCardEntry.cs:69-94）→ `CardFactory.CreateForMerchant(player, pool.Except(已上架), CardType)`（CardFactory.cs:40-60）：先 `Hook.ModifyMerchantCardPool`→排除 Basic→`FilterForPlayerCount`→Shop 稀有度掷骰（CardRarityOdds.cs:96-111，`RollWithoutChangingFutureOdds`）→`GetNextAllowedRarity`（CardFactory.cs:263-281）→`NextItem` 随机选一张。候选池 = `Player.Character.CardPool.GetUnlockedCards(Player.UnlockState, constraint)`（MerchantInventory.cs:101）→ `JainaCardPool.AllCards`（CardPoolModel.cs:44-55）= 基类 `GenerateAllCards`（Jaina 未重写 `CardTypes`，RL:Scaffolding/Content/TypeListCardPoolModel.cs:78-89 为空）+ `ModHelper.ConcatModelsFromMods`（0.111.1:Modding/ModHelper.cs:78-93）把 `[RegisterCard]` 注册的类型经 `ModelDb.GetById<CardModel>(ModelDb.GetId(t))` 拼入。

**H1（最可能）— Frostbolt 不在 `JainaCardPool.AllCards` 里（注册/池拼接问题）**。具体机制候选：(a) `ModHelper.ConcatModelsFromMods` 首次枚举时把池置为 `isFrozen=true`（ModHelper.cs:86），若某系统在自动注册（`LocManager.Initialize` 的 `ModTypeDiscoveryHub.RunOnce`）完成前触碰了 `AllCards`，之后任何 `ModHelper.AddModelToPool` 都会抛 "too late"（ModHelper.cs:64-67）——会按注册顺序漏掉部分卡；(b) 若 Frostbolt 类型未进 `ModelDb._contentById`（ModelDb.Init 的 `AllAbstractModelSubtypes`＝`ReflectionHelper.GetSubtypesInMods<AbstractModel>()`，ModelDb.cs:68-88、ReflectionHelper.cs:38-53），`ConcatModelsFromMods` 的 `GetById` 抛 `ModelNotFoundException`（ModelDb.cs:549-553）——但这会让整池枚举失败、商店一张 Jaina 卡都没有，与"其他卡在"矛盾，故 (b) 概率低。**验证**：修复 [JainaDiag] 后看 `pool card: ...frostbolt...` 行是否存在；或临时在 `Entry.Init` 直接打印 `ModelDb.CardPool<JainaCardPool>().AllCardIds` 与 `ModHelper` 注册数量（RitsuLib 日志中 `[Content] Registered card: ...` 应有 Frostbolt 行）。

**H2 — 池被过早冻结（AllCards 首次访问时机）**。`CardModel.Pool` getter（CardModel.cs:298-317）会枚举 `ModelDb.AllCardPools` 各池的 `AllCardIds`→`AllCards`，任何早期访问（如 `ModelDb.Preload` 前被某系统触发）都会冻结池。**验证**：查 RitsuLib/游戏日志中注册后是否出现 "Tried to add model ... too late" 异常；把 `ModTypeDiscoveryHub.LogDiagnostics()`（RL:Interop/ModTypeDiscoveryHub.cs:91-114）挂到 `MainMenuReadyEvent` 打印注册快照。

**H3（代码已基本排除）— 运行时 Type/Rarity 异常**。`Frostbolt` 经 `JainaSpellCardTemplate`（不重写 `Type/Rarity`）→ `CardModel(int,CardType,CardRarity,TargetType,bool)` 构造存字段（CardModel.cs:1087-1094），`Type=Attack`、`Rarity=Common` 确定；动态 `CardType.Minion` 值在高值带不冲突。**验证**：diag 的 `type={c.Type} rarity={c.Rarity}` 行直接给出答案。

**H4（原版已排除，跨 mod 无法排除）— 模型 ID slug 冲突**。`ModelDb.GetEntry(Type)`＝`Slugify(type.Name)`（ModelDb.cs:535-538），`ModelDb.Init` 的 `_contentById[id]=value` 后者覆盖前者（ModelDb.cs:423-432）。已对 0.111.1 全库 grep `Frostbolt|frostbolt`：**0 命中**，原版无冲突；若其他 mod 定义了同名 `Frostbolt` 卡，后加载者会覆盖 `("card","frostbolt")` 的实例。**验证**：diag 打印 `c.Id` 与 `c.GetType()`，对比是否为 `jaina...Frostbolt`。

**H5 — 统计/观察点问题**。商店每局只刷 2 张攻击槽，`ApexisBlast` 与 `Frostbolt` 各约 50% 概率；样本少时长期不见 Frostbolt 并非不可能。若用户观察的是"卡牌图鉴/卡池列表"而非实际商店，路径不同（图鉴走 `ModelDb.AllCards`+池过滤，不经 `CreateForMerchant`）。**验证**：多开若干局商店统计；先确认观察点是"商店货架"还是"图鉴"。

## 改进机会（0.111.1 新 API 可替代/增强现有实现）

1. **诊断事件替换**：`GameReadyEvent` 在 `NGame._Ready`（0.111.1:NGame.cs:182）发布、早于内容就绪；改用 RitsuLib 的 `ModelRegistryInitializedEvent`（RL:GameLifecycleContracts.cs:96-99，在 `ModelDb.Init` Postfix 发布，RL:CoreLifecyclePatches.cs:156-169）或 `RunStartedEvent`（RL:GameLifecycleContracts.cs:232-237，`RunManager.InitializeNewRun` Postfix，RL:CoreLifecyclePatches.cs:303-342）做卡池诊断，语义与"商店候选"更贴合。
2. **商店候选观测点**：0.111.1 提供 `Hook.ModifyMerchantCardPool` / `Hook.ModifyMerchantCardRarity`（CardFactory.cs:46,50,71,75）与 `Hook.ModifyMerchantCardCreationResults`（MerchantCardEntry.cs:92,108）作为商店生成钩子；在这些钩子（或 `CardFactory.CreateForMerchant` Prefix）打日志，比事后枚举 `AllCards` 更精确——能直接看到每次商店生成的 `options/rarity/type` 与最终选中卡。
3. **卡池解锁过滤**：0.111.1 的 `CardPoolModel.FilterThroughEpochs` 是 `protected virtual`（CardPoolModel.cs:119-122）；JainaCardPool 可 override 实现自定义解锁/过滤，替代对 RitsuLib 全局 `CardUnlockFilterPatch`（RL:UnlockIntegrationPatches.cs:58-77）的隐式依赖。
4. **商店 Power 槽**：`MerchantPowerSlotPatch` 的全局行为（对任何无 Power 卡角色生效）可改为 JainaCardPool 上的 virtual 属性（如 `ShopFallbackCardType`），或直接利用 0.111.1 的 `Hook.ModifyMerchantCardPool` 在池级注入一张占位 Power 卡，避免全局 patch。
5. **关键词显示**：`ModKeywordRegistry.RegisterOwned` 支持 `ModKeywordCardDescriptionPlacement.BeforeCardDescription`（RL:Keywords/ModKeywordRegistry.cs:154-175、306-307 + `ModKeywordCardDescriptionPatches`），Jaina 目前刻意不注入卡面描述（`JainaKeywords.cs:12-14` 注释）；若未来想让"法术牌/冰霜"等词条以金色样式出现在卡面而非仅悬停，可直接开启该 placement，无需自绘。

## 结论摘要

1. Jaina 用到的 RitsuLib 运行时 API（`HoverTipFactory.FromKeyword` 补丁、`ModCardTemplate.AdditionalHoverTips`/`ExtraHoverTips`、`CanonicalKeywords/CanonicalVars`、`RegisterOwnedCardKeyword` 动态关键词、`ModCharacterTemplate`/`IModCreatureVisualsFactory`、`ModRelicTemplate`/`BeforeCombatStart`、`RegisterRelic` 池注册）在 0.111.1 反编译源码中**全部存在且签名、语义匹配**，无 MissingMethod 级兼容性问题；动态枚举（CardType/CardKeyword/TargetType）的高值保留带机制与 0.111.1 的 int 枚举完全兼容。
2. **[JainaDiag] 静默**不是 mod 代码错误，而是 `GameReadyEvent` 在用户运行时未发布——最可能是部署的 RitsuLib variant 与源码树版本错配，或框架 critical 补丁失败回滚；需先在订阅处加"subscribed"日志并把诊断改挂 `ModelRegistryInitializedEvent`/`RunStartedEvent` 定位。
3. 商店候选链路在 0.111.1 逐行核对成立（Shop 稀有度含 Common、GetNextAllowedRarity 可回绕、Frostbolt 的 Type/Rarity/MultiplayerConstraint 均满足），Frostbolt 缺失最可能落在"池拼接/注册（H1-H2）"或"观察样本（H5）"，已给出可验证的排查步骤；修复诊断后第一屏输出即可定性。
