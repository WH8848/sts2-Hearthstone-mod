# MinionLib 0.6.2 × Jaina 随从流程审计（0.111.1）

> 审计对象：Jaina 随从从实际使用流程出发，逐项核对 **MinionLib 0.6.2**（NuGet `FuYnAloft.Sts2.MinionLib 0.6.2`，本地源码 `E:\MOD\sts2\MinionLib`，另以 DLL 反射确认发布版 API 面）与 **0.111.1**（`E:\MOD\sts2\sts2\0.111.1\src`，3545 cs）的联动。Harmony patch 目标方法名按反编译结果核对（不区分大小写、含私有方法）。
> 交叉引用：`docs/audit-0.111.1/audit-01-minion-system.md`（随从系统主审计）。本文聚焦 MinionLib 联动面，重叠结论从简、注明出处。

## 潜在 Bug / 行为差异（mod 逻辑 vs 0.111.1 语义）

1. **亡语/死亡清理死路径（承接上文"高 1"）**：`AfterDamageReceivedLate` 的整段死亡处理（亡语触发 + `Creature.Powers` 逐个 `PowerCmd.Remove` + `combatState.RemoveCreature(Creature, true)` + `CombatManager.RemoveCreature`，JainaMinionBase.cs:436-473）对致命伤害**永不执行**。附带影响：Aegwynn +2 力量永久残留、VolatileSkeleton 爆炸亡语/ Mozaki 力量返还永不触发。核心流程已覆盖其中大部分清理（`RemoveAllPowersAfterDeath` 清随从自身 Powers 并触发 `AfterRemoved`，CreatureCmd.cs:566-570；`PlayerCombatState.OnPetDied` 自动从 `_pets` 摘除，PlayerCombatState.cs:281-292；MinionKillPatch 清 CombatManager/CombatState），唯一缺失的正是"亡语"。
2. **`VolatileSkeleton.OnDeathrattle` 的 `!Creature.IsAlive` 守卫自相矛盾**（VolatileSkeleton.cs:50）：亡语按语义在死亡后触发，守卫会让任何基于 AfterDeath 的修复方案直接失效；修复时需一并删除（或改为只判 `Creature.CombatState == null`）。
3. **`AfterDamageReceivedLate` 内的 `combatState.RemoveCreature(Creature, true)` detach 语义**（JainaMinionBase.cs:467）：0.111.1 `CombatState.RemoveCreature` 的 `unattach: true` 会把 `creature.CombatState = null`（CombatState.cs:300-303），随从无法再入战。当前因死路径永不执行而无实害；若按"高 1"迁移到 AfterDeath，**不要**在 AfterDeath 里做 detach（核心 `KillWithoutCheckingWinCondition` 仍在收尾：`Hook.AfterDeath` 之后还有 `RemoveAllPowersAfterDeath`、Enemy 侧移除判定 CreatureCmd.cs:556-563），交给 MinionKillPatch 收尾即可。
4. **意图链路整体依赖（承接"中 1"）**：NextMove 不填充 → `RefreshIntentDisplay` 实际刷的是空意图（NCreature.cs:290）。audit-01 高 1/潜在 Bug 3 已详述（含 `CombatStateTracker.CombatStateChanged` 延迟一帧、`RevealIntents` 淡入重播导致的"闪烁"）。MinionLib 联动面补充：MinionLib 0.6.2 无任何 NextMove 填充路径（源码仅 `MinionModel.GenerateMoveStateMachine` 产出 IDLE 状态，不触 RollMove），此问题需 Jaina 自行解决，不能指望 MinionLib。
5. **意图数值标签与伤害口径**（audit-01 中 1/中 2）：`JainaConditionalAttackIntent` 非 `AttackIntent`，0.111.1 `NIntent` 数值标签分支不渲染（NIntent.cs:135）；显示伤害走 `Hook.ModifyDamage(ValueProp.Move)` 吃力量、命中走 `ValueProp.Unpowered` 不吃。与 MinionLib 无关，纯 mod 显示层，引用 audit-01 不再展开。
6. **`PowerCmd.Apply<MinionPower>` 对玩家侧 Pet 为惰性标记**（JainaMinionBase.cs:311-312）：`MinionPower.OwnerIsSecondaryEnemy` 只对 `Side == CombatSide.Enemy` 生效（Creature.cs:269-278），玩家侧随从不参与击杀/胜负结算判定，此调用无副作用也无必要（可保留作防御性标记）。0.111.1 `MinionPower` 为 sealed（MinionPower.cs:5），无法子类化扩展（因此亡语修复只能走 `AfterDeath` override，不能借 MinionPower 挂钩）。

## 改进机会（0.111.1 新 API 可替代/增强现有实现）

1. **亡语改挂 `AbstractModel.AfterDeath`**：0.111.1 `Hook.AfterDeath` 遍历全部 hook listener（Hook.cs:462-476），随从 Monster 天然在列（CombatState.IterateHookListeners，CombatState.cs:411-421），且触发时机在 `RemoveAllPowersAfterDeath`（CreatureCmd.cs:566）之前、死亡动画开始之后——是亡语的标准挂点。配合删除 `OnDeathrattle` 的 IsAlive 守卫即可让三个亡语随从在 0.111.1 下真正生效。
2. **意图自举**：`Creature.PrepareForNextTurn(IEnumerable<Creature>, bool rollNewMove = true)`（Creature.cs:547-559）在 `OnSummon` 末尾调用一次，RollMove 会填充 `NextMove`（含 JainaConditionalAttackIntent），此后 `NCreature.UpdateIntent`（NCreature.cs:284-312）与 0.111.1 原生揭示流程（`PerformIntent` 冻结 / `RevealIntents` 淡入）全部可用，彻底摆脱对 RitsuLib 意图管理器的隐式依赖（audit-01 改进 2 同）。
3. **意图数值角标**：RitsuLib `IIntentExtraCornerAmountLabelsProvider`/`SpecsProvider`（项目内 ritsulib-r6/r7 文档）在 `JainaConditionalAttackIntent` 上绘制攻击数值，绕开 0.111.1 `NIntent` 的 AttackIntent/StatusIntent 专用标签分支（NIntent.cs:117-137）。
4. **死亡清理瘦身**：0.111.1 核心（`RemoveAllPowersAfterDeath` + `OnPetDied` + MinionKillPatch）已覆盖随从死亡的全部状态清理，Jaina 侧 AfterDamageReceivedLate 的清理代码可整体删除或保留为注释说明（避免误导后人以为亡语在这触发）。
5. **`MonsterModel.IntendsToAttack`**（MonsterModel.cs:242-246）+ RitsuLib `AnyAttackingEnemy`：若未来 Jaina 随从参与"敌方攻击意图"类交互，可直接复用 0.111.1 原生语义。
6. **MinionLib 行动队列**：0.111.1 `ActionQueueSynchronizer.RequestEnqueue`（ActionQueueSynchronizer.cs:146）与 `ActionSynchronizerCombatState.PlayPhase`（ActionSynchronizerCombatState.cs:16）签名未变，MinionLib `ExecuteCreatureActionGameAction` 队列链路（含网络重放 `NetExecuteCreatureActionGameAction`）在 0.111.1 可用；后续若做联机支持无需改 MinionLib。

## 结论摘要

1. 七条链路逐一核对：**召唤链（PlayerCmd.AddPet<T> / PetOwner / Side / IsPet / CombatSide）、OnSummon 时序（MinionSummonOptions / SetMaxAndCurrentHp）、行动点（BeforeSideTurnStart / PowerCmd.Apply / Decrement / AutoRemoveAtTurnEnd）、敌人回合状态机隔离（TakeTurn 仅限 Enemy）、视觉工厂（IModCreatureVisualsFactory → NCreatureVisuals %Visuals/%Bounds/%CenterPos/%IntentPos）、悬停面板（LocString / HoverTipFactory / ModelDb）在 0.111.1 全部存在且签名一致，无 MissingMethodException 级风险**；MinionLib 0.6.2 全部 20+ 个 Harmony patch 目标方法在 0.111.1 均存在（含私有 `KillWithoutCheckingWinCondition`、`AllowedToTargetCreature`、`NPotionHolder.TargetNode` 等）。
2. **唯一高危项是亡语死路径**：`AfterDamageReceivedLate` 对致命伤害不触发（0.111.1 CreatureCmd.cs:414-421），三个亡语随从的死亡效果与 Aegwynn 力量回收实际从未生效——需改挂 `AfterDeath` 并删除 `OnDeathrattle` 的 IsAlive 守卫（0.109.1~0.111.1 三版同源，属 mod 逻辑缺陷，非 0.111.1 新回归）。
3. 两个中危项均为"依赖外部机制/双计数"类：NextMove 意图填充依赖 RitsuLib 意图管理器（建议 OnSummon 自举 `PrepareForNextTurn(rollNewMove: true)`）、手动模式行动次数双计数（建议以 `JainaAttackAction.Amount` 为唯一事实源）。
4. 环境核对通过：运行期 MinionLib = 0.6.2 与编译期一致；RitsuLib 0.5.12（运行）vs 0.5.11（编译）建议升级编译以对齐 0.111.1 API 面。
5. 总体：Jaina 随从的召唤/行动/死亡状态清理/视觉/悬停在 0.111.1 可安全运行；亡语修复 + 意图自举是本次审计给出的两个必做项，其余为显示层与健壮性建议。
