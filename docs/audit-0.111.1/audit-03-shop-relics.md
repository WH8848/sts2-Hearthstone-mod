## 潜在 Bug / 行为差异（mod 逻辑 vs 0.111.1 语义）

1. **打折槽位概率变化**：`MerchantInventory.PopulateCharacterCardEntries` 用 `PlayerRng.Shops.NextInt(_coloredCardTypes.Length)` 挑一个槽打折（MerchantInventory.cs:100-110）。0.111.1 是 5 槽（1/5），若商店修复方案按旧版 3 槽假设写死了索引，会错位；当前 mod 未涉及，仅提示。
2. **`BeforeCombatStart` 阶段抽牌**：`EvenMatchAncient` 在 `BeforeCombatStart` 里 `CardPileCmd.Draw(new ThrowingPlayerChoiceContext(), 1, Owner)`。0.111.1 中 `Hook.BeforeCombatStart` 在 `CombatManager` 战斗状态初始化后调用（`src/Core/Combat/CombatManager.cs:594` → `src/Core/Hooks/Hook.cs:311-315`），此时手牌/抽牌堆已就绪，游戏内 `BeforeCombatStart` 钩子均在此阶段执行（如 VenerableTeaSet 加能量、SneckoEye 洗牌），抽牌可用。语义一致，无兼容风险。
3. **`ModelDb.GetById<LuckyCoin>(ModelDb.GetId(typeof(LuckyCoin)))`**：0.111.1 中 `GetId(Type)`（`src/Core/Models/ModelDb.cs:515`）与 `GetById<T>`（:549，`where T : AbstractModel`）均存在；LuckyCoin 经 RitsuLib 在启动期注册进 ModelDb，`BeforeCombatStart` 首次触发必然晚于注册，不会 MissingMethod/未注册异常。该两段式写法与 RitsuLib 自身 `ResolveModels`（`ModCharacterTemplate.cs:830-831`）同构，正确。
4. **补丁的多人语义**：`CreateForMerchant` 的稀有度/选卡使用 `player.PlayerRng.Shops`（`CardFactory.cs:50-57`），每客户端本地独立掷骰；Prefix 的类型替换是确定性判定（同卡池 ⇒ 同结论），不会造成联机分歧，与 mod 注释一致。
5. **`JainaCastTracker.MarkGenerated` 空操作**：LuckyCoin 是 `CardType.Skill`，会被记录（`JainaCastTracker.cs:93-96` 仅跳过非 Attack/Skill）；`CardPileCmd.AddGeneratedCardToCombat(coin, PileType.Hand, Owner)` 在 0.111.1 返回 `CardPileAddResult`，mod 忽略返回值与游戏内多数调用一致（如 `Abundance.cs:40`）。无差异。
6. **`CanBeGeneratedInCombat`**：`CardModel.CanBeGeneratedInCombat` 默认 `true`（`src/Core/Models/CardModel.cs:643`），且 0.111.1 的 `CardFactory.FilterForCombat` 只排除 Basic/Ancient/Event（`CardFactory.cs:159-162`）——**Token 卡可被战斗内随机生成效果选中**。LuckyCoin 在 JainaNeutralCardPool，`GetDefaultTransformationOptions` 对 Token 稀有度会回退到无色池（`CardFactory.cs:172`），不会直接进吉安娜的随机生成；但若未来有"从角色池随机生成卡"的效果，需注意。

## 改进机会（0.111.1 新 API 可替代/增强现有实现）

1. **官方 hook 替代 Harmony Prefix**：0.111.1 提供 `Hook.ModifyMerchantCardPool`（`Hook.cs:1803`）、`Hook.ModifyMerchantCardRarity`（`Hook.cs:1815`）、`Hook.ModifyMerchantCardCreationResults`（`Hook.cs:1792`）。可在角色/卡池模型上实现 `ModifyMerchantCardRarity`（把 Power 槽掷出的稀有度强制改为有候选的类型）或 `ModifyMerchantCardCreationResults`（创建后整体替换），比 patch `CardFactory.CreateForMerchant` 更贴近官方扩展点；注意前两者无法解决"某类型零候选 → `None` 抛异常"，仍需类型替换或保证每类型 ≥1 张非 Basic 卡。
2. **更稳的商店修复落点**：直接 patch `MerchantCardEntry.Populate`（`MerchantCardEntry.cs:69-94`）或 `MerchantInventory.PopulateCharacterCardEntries`（`MerchantInventory.cs:98-112`），在 Power 槽无候选时改为跳过/换类型，可一并覆盖"双 Attack/Skill 槽候选不足"的场景；代价是改动面比当前 Prefix 大。
3. **升级 RitsuLib**：`TouchOfOrobasGetUpgradedStarterRelicPatch`（`_reference\RitsuLib\src\Relics\Patches\TouchOfOrobasGetUpgradedStarterRelicPatch.cs:27-29`）的目标 `(typeof(TouchOfOrobas), nameof(GetUpgradedStarterRelic), [typeof(RelicModel)])` 与 0.111.1 完全一致，映射链路（`RegisterTouchOfOrobasRefinementMapping` → Prefix 短路返回模组模板 → `TouchOfOrobas.AfterObtained` 用其 `.Id` 经 `ModelDb.GetById` + `ToMutable` 替换，`TouchOfOrobas.cs:154-161`）在 0.111.1 原样可用；唯一缺口是 RitsuLib 整体按 0.110.0 编译，等官方 0.111.1 兼容包即可。
4. **初始卡组/遗物机制已走官方属性**：RitsuLib `ModCharacterTemplate` 以 `sealed override` 实现 `CharacterModel.StartingDeck/StartingRelics`（`ModCharacterTemplate.cs:394-397/835-855`），`Player.PopulateStartingDeck`（`Player.cs:711-721`）/`PopulateStartingRelics`（`Player.cs:743-752`）与 `RunManager.FinalizeStartingRelics`（`RunManager.cs:725-738`，对新开档逐遗物调用 `AfterObtained()`）均按官方属性读取——`RegisterCharacterStarterRelic`/`RegisterCharacterStarterCard` 的 `Order` 参数（`RegistrationAttributes.cs:367/383`）可用于控制初始排序，未来调整初始卡组顺序时可利用。
5. **防止 LuckyCoin 被随机生成**：如需彻底隔离，可覆写 `CanBeGeneratedInCombat => false`（0.111.1 `CardModel.cs:643` 默认 true）——目前 Token 稀有度不在 `FilterForCombat` 的排除列表中。

## 结论摘要

- 7 项核对全部通过：`CardFactory.CreateForMerchant(Player, IEnumerable<CardModel>, CardType)`、商店流程（`MerchantInventory`/`MerchantCardEntry`/`PopulateCharacterCardEntries`/`_coloredCardTypes`/`GetNextAllowedRarity`/`RollWithoutChangingFutureOdds`）、`CardRarity` 枚举与 `Rarity != Basic` 过滤、`RelicModel.BeforeCombatStart()`、`TouchOfOrobas.GetUpgradedStarterRelic(RelicModel)`/`RefinementUpgrades` 与 RitsuLib 0.5.11 映射补丁、`CardPileCmd.AddGeneratedCardToCombat`/`ICombatState.CreateCard`/`ModelDb.GetId/GetById`、初始卡组/遗物（`StartingDeck`/`StartingRelics` 官方机制 + RitsuLib 属性合并）在 0.111.1 中全部存在且签名一致，无 MissingMethodException 风险。
- 无高危兼容性问题；两项中危：RitsuLib 0.5.11 按 0.110.0 API 面编译（本模块对接点未变，但整体需冒烟），以及商店 5 槽结构下"同类型第二槽候选不足仍会抛异常"这一补丁未覆盖的脆弱点。
- 商店修复方案在 0.111.1 上有效：Power 槽仍在（`_coloredCardTypes[4]`），Prefix 把 `type` 改为动态枚举 `JainaCardTypes.Minion` 后，`CreateForMerchant` 的 `c.Type == type` 匹配随从卡（`JainaMinionCardTemplate.Type` 覆写返回该动态值），随从卡在 Common/Uncommon/Rare 均有候选，且显示链路（`CardTypeExtensions.ToLocString` 等 4 个补丁目标）完好。
- 初始遗物升级链路原样可用：欧罗巴斯之触 `AfterObtained` → `GetUpgradedStarterRelic` 被 RitsuLib Prefix 短路为 `EvenMatchAncient` 映射，`EvenMatch`（Starter）/`EvenMatchAncient`（Ancient）稀有度与 `GetStarterRelic` 的 `Rarity == Starter` 判定匹配。
- 建议后续动作：升级 RitsuLib 到 0.111.1 兼容版并冒烟；将商店补丁的"无 Power"判定口径改为"无非 Basic Power 候选"，并考虑把同类型第二槽的候选校验纳入商店修复方案。
