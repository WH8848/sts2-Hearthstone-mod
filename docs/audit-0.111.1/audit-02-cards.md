## 潜在 Bug / 行为差异（mod 逻辑 vs 0.111.1 语义）

1. **压轴判断时机依赖"能量已先扣"**：0.111.1 中 `PlayCardAction.ExecuteAction` 先 `SpendResources`（PlayCardAction.cs:92）再 `OnPlayWrapper`（:103），因此 OnPlay 内读 `Energy` 是扣费后的值——mod 的 `Energy <= 0` 方向正确；偏差仅在"0 费牌 + 起始 0 能量"的误触发（见上文中危条目）。
2. **MinionLib Harmony 目标签名核对（全部通过，需回归）**：`NTargetManager.AllowedToTargetCreature(Creature)` 私有（`Core/Nodes/Combat/NTargetManager.cs:275`）、`NCardPlay.TryPlayCard(Creature?)` 受保护（`NCardPlay.cs:55`）、`NCardPlay.ShowMultiCreatureTargetingVisuals()` 受保护（`:186`）、`NMouseCardPlay.SingleCreatureTargeting(TargetMode, TargetType)`/`MultiCreatureTargeting(TargetMode)` 私有 async Task（`NMouseCardPlay.cs:215/269`）、`NControllerCardPlay.SingleCreatureTargeting(TargetType)` 私有 async Task（`NControllerCardPlay.cs:100`）、`NControllerCardPlay.MultiCreatureTargeting()` 私有 **void**（`:183`，MinionLib 的 `ControllerMultiCreatureTargetingPrefix` 未声明 `ref Task __result`，void 签名可绑定）、`CardModel.IsValidTarget(Creature?)`（`CardModel.cs:1762`）、`ActionTargetExtensions.IsSingleTarget(TargetType)`（`Core/Entities/Cards/ActionTargetExtensions.cs:5`）、字段 `NTargetManager._validTargetsType`（`NTargetManager.cs:52`）、`NCardPlay.Card`/`Holder`/`Cleanup(bool)`（`NCardPlay.cs:42/38/139`）。全部存在且签名匹配，无 MissingMethod 风险；但均为按名（name-based）patch，升级后需跑一遍手牌指向型法术（火球/寒冰箭）的鼠标与手柄目标选择回归。
3. **动态 CardType.Minion 的 switch 暴露面**：0.111.1 中对 `CardType` 做 switch 并抛 `ArgumentOutOfRangeException` 的位置为 `CardTypeExtensions.ToLocString`（`Core/Entities/Cards/CardTypeExtensions.cs:9-31`）、`CardModel.FramePath`（`CardModel.cs:159-186`）、`PortraitBorderPath`（`:190-213`）、`AncientTextBgPath`（`:217-245`）——JainaCardTypePatches 的 4 个 Prefix 已全部覆盖（`JainaCardTypePatches.cs:19-83`）；`MadScience.GetPortraitFilename`（`Core/Models/Cards/MadScience.cs:179`）与 `TinkerTime.ChooseRiderEffect`（`Core/Models/Events/TinkerTime.cs:115`）的 switch 只处理游戏自身存储的类型值，不消费 mod 卡的 Type，无风险。但注意 0.111.1 中 `FramePath`/`PortraitBorderPath`/`AncientTextBgPath` 均为 **private getter**（Harmony 可 patch，patch 代码无编译期绑定，故无碍）。
4. **FreezingPotion 双生复制依赖 CreateClone 保留 Owner**：0.111.1 中 `CardModel.CreateClone()`（`CardModel.cs:2182`）要求卡已在战斗牌堆（OnPlay 期间卡在 Play 堆，满足），克隆保留原 Owner（`CreateCloneForPlayer` 注释明确"normally clone cards retain the same player"），`AddGeneratedCardToCombat` 要求克隆 `Pile == null` 且 `CombatManager.IsInProgress`（`CardPileCmd.cs:288-294`）——均满足；若未来克隆改走 `ToMutable()`（无 Owner），会重蹈 mod 注释中提到的入牌堆 NRE，建议后续改用显式的 `CreateCloneForPlayer(base.Owner)`（`CardModel.cs:2199`）更稳。
5. **NorgannonWisdom 的 `TryModifyEnergyCostInCombat` 与其它全局减费监听器互相覆盖**：0.111.1 中 `Hook.ModifyEnergyCostInCombat` 顺序遍历所有战斗内模型并逐个覆盖 `modifiedCost`（`Core/Hooks/Hook.cs:1583-1599`），`NorgannonWisdom.cs:56-61` 在三派系集齐时强制置 0 会覆盖 SorcererApprentice 等的减费结果（反之亦然）；顺序不可控，建议把"置 0"逻辑放到 `TryModifyEnergyCostInCombatLate`（`AbstractModel.cs:2049`）或改为相对减费 `originalCost - ...`。
6. **Frostbolt 冰枪术 0 费分支**：升级后 `DamageVar.BaseValue = 0`（`Frostbolt.cs:101`），若目标无冻结则只上 1 层冻结不造成伤害，与卡面一致，但 `CanonicalVars` 仍展示 `DamageVar(3m)` 升级前数值——0.111.1 中 `CardModel.Description` 在升级预览时用 `DynamicVars`（`CardModel.cs:1375-1378`），升级后描述中的 `{Damage}` 会显示 0，属于展示与"冰枪术"卡面（每层冻结 4 伤）不符的已知简化，非兼容性问题。

## 改进机会（0.111.1 新 API 可替代/增强现有实现）

1. **Discover 改用官方卡生成管线**：0.111.1 提供 `CardCreationOptions` record（`Core/Runs/CardCreationOptions.cs:18`，含 `WithFilter(Func<CardModel,bool>)` :154、`WithCardPools` :143、`WithFlags` :163、`WithRarityOdds` :172、`WithRngOverride` :178）与 `CardFactory.CreateForReward(Player, int, CardCreationOptions)`（`Core/Factories/CardFactory.cs:89`），再配 `CardSelectCmd.FromChooseACardScreen`（`Core/Commands/CardSelectCmd.cs:252`）。可替代 `JainaDiscoverHelper` 硬编码的 5 张 `AttackSkillPool`（`JainaDiscoverHelper.cs:23-30`），获得稀有度概率、卡池注册表过滤、商店/事件复用与重掷支持。
2. **多段攻击/随机攻击改走 `AttackCommand` 构建器**：`WithHitCount(int)`（`AttackCommand.cs:488`）、`TargetingRandomOpponents(ICombatState, bool)`（`:322`）、`TargetingAllOpponents(ICombatState)`（`:294`）、`OnlyPlayAnimOnce()`（`:478`）、`BeforeDamage(Func<Task>)`（`:499`）可一次性重构 Fireblast 灌注循环与 FlameWard 烈焰风暴，使攻击历史/钩子/音画语义正确（见中危/低危条目）。
3. **双生法术/衍生物批量接口**：`CardPileCmd.AddGeneratedCardsToCombat(IEnumerable<CardModel>, PileType, Player?, CardPilePosition)`（`CardPileCmd.cs:281`）可一次入多张；`CardModel.CreateCloneForPlayer(Player)`（`CardModel.cs:2199`）显式携带 Owner，替代"CreateClone 后祈祷保留 Owner"的隐式约定。
4. **压轴语义接入官方能量钩子**：`Hook.AfterEnergySpent(ICombatState, CardModel, int)`（`Core/Hooks/Hook.cs:532`）/ `AbstractModel.AfterEnergySpent(CardModel, int)` 与 `CardPlay.Resources.EnergySpent`（`CardPlay.cs:39`）比 OnPlay 内猜 `Energy <= 0` 更精确；`ResourceInfo` 结构见 `Core/Entities/Cards/ResourceInfo.cs`。
5. **费用展示与结算的正式钩子已就位**：`TryModifyEnergyCostInCombat(CardModel, decimal, out decimal)`（`AbstractModel.cs:2034`）与 `TryModifyEnergyCostInCombatLate`（`:2049`）在 0.111.1 中被 `Hook.ModifyEnergyCostInCombat`（`Hook.cs:1583`）与 `CardCostHelper.cs:109` 调用，ApexisBlast/FlameWard/NorgannonWisdom 的用法（含 `ReferenceEquals(card, this)` 守卫）与游戏内 Eldolon/BulletTime 等模式一致，可继续沿用；如多 mod 并存建议用 Late 版做最终覆盖。

## 结论摘要

- 9 项核对清单全部通过：`DamageCmd.Attack` 链（`FromCard/Targeting/WithHitFx/Execute` 签名逐一匹配，含 `WithHitFx` 第 3 参 `tmpSfx`）、`CardEnergyCost` 全部方法与 `TryModifyEnergyCostInCombat`、`PowerCmd.Apply` 双重载、`CardPileCmd.AddGeneratedCardToCombat(Player?)`/`CreateClone`/`AddKeyword`/`RemoveKeyword`、Discover 全套 API、`TargetType` 枚举与 MinionLib 全部 Harmony 目标（含私有方法）、`OnPlay(PlayerChoiceContext, CardPlay)` 与 `CardPlay.Target/Owner` 结构、`DynamicVar/DamageVar/CardsVar/BlockVar` 与 `{IfUpgraded:show:...}` 格式化器在 0.111.1 均存在且签名一致，**无高危（MissingMethodException）兼容性问题**。
- 2 个中危行为差异：冻结对随从攻击无效（`IsPoweredAttack` 守卫 + 随从攻击用 `Unpowered`）；压轴 `Energy <= 0` 对 0 费巅峰无限会误触发。
- 4 个低危问题：压轴发现来源取整手牌、倒带复制品丢失升级、多段/随机伤害未走单次 `AttackCommand`、召唤 fire-and-forget。
- 主要改进方向：Discover 改用官方 `CardCreationOptions`/`CardFactory` 管线；多段与随机攻击改用 `WithHitCount`/`TargetingRandomOpponents`；压轴条件改用 `cardPlay.Resources.EnergySpent` 或 `AfterEnergySpent` 钩子。
- 结论：该批法术/技能卡可在 0.111.1 上直接运行，建议优先修复冻结-随从与压轴两处语义，其余为体验与规范性问题。
